# Presentation Framework — AKS Migration Agent

Companion guide to [`AKS_Migration_Agent_OnePager.pptx`](./AKS_Migration_Agent_OnePager.pptx)
(generated by [`build_onepager.py`](./build_onepager.py)). The deck is a single
slide by design — this document is the framework a presenter uses to deliver
it: the narrative arc, the talking points behind each card, anticipated
questions, and pitches at three different lengths.

Audience: **leadership / stakeholders.** Optimise for business value, risk
reduction and a clear ask — not implementation detail. If a technical
follow-up is needed, use the [README](../README.md) and
[`AGENTIC_FRAMEWORK.md`](../AGENTIC_FRAMEWORK.md), and offer a live
`./run.sh demo` instead of more slides.

---

## 1. The narrative arc

Five beats, in order, regardless of how much time you have:

1. **Cost of the status quo** — migrations are manual, slow, and — the
   uncomfortable part — *even careful ones ship defects*.
2. **What we built** — a seven-stage agent loop with a mandatory LLM step
   that generates/refines the actual migrated files, bounded to what the
   deterministic rules already flagged, and never trusted before the fact.
3. **Proof, not a promise** — benchmarked against a migration a Spark
   engineer already built and shipped, not a synthetic demo.
4. **Why it's safe to say yes to** — every LLM edit is re-validated after
   generation and reverted if it fails; it cannot touch a cluster or push
   code; a human always approves.
5. **The ask** — a bounded, low-risk pilot on more applications.

Land on the ask. Don't end on the roadmap slide-card — end on beat 5, spoken.

## 2. Elevator pitches (pick one for the time you have)

**30 seconds:**
> "We built an agent that turns an OpenShift-to-AKS migration into a
> repeatable, scored pipeline instead of a manual, one-off effort. Run
> against a migration one of our own engineers already did by hand, it found
> twelve production-blocking defects — including a committed secret and a
> container running as root — that shipped anyway. It touches nothing in
> production, and every result needs a human sign-off before anything
> merges. And once we're happy with a result, we can freeze it — the same
> input reproduces the exact same output, byte-for-byte, forever."

**1 minute:** add —
> "It works by walking the repo, classifying every file, then running
> seventeen deterministic rules — eight that translate OpenShift constructs
> to their AKS equivalent, nine that catch defects OpenShift tolerated but
> AKS won't. An LLM then reviews and finishes exactly the files those rules
> already flagged — it doesn't roam free over the repo — and every one of
> its edits is re-validated afterwards; if an edit fails, it's automatically
> reverted to the deterministic version, never silently kept. Everything is
> config-driven, so onboarding a new application is a YAML change, not new
> code. And it doesn't guess: anything it isn't sure about — a target
> resource name, a missing ingress host — it flags for a human instead of
> inventing an answer."

**3 minutes:** add —
> "We scored it against the human-verified branch of that same migration at
> 86.3% file-level fidelity — our target for sign-off is 90%, and the gap is
> visible and explainable, not a black box. It also produces a migration
> workbook — namespaces, storage types, routes, databases, owners,
> dependencies — mapped straight to their Azure equivalents, which is
> normally a spreadsheet somebody builds by hand. On idempotency: an LLM
> isn't naturally deterministic, so we built a freeze mechanism — confirm a
> result once, and every run after that replays it exactly, in seconds
> instead of minutes, with no further model calls. That's proven end to end:
> two separate runs, same input, matching file hashes. Today all of this is
> proven on one real application. The ask is a sponsored pilot on a handful
> more, so we can widen rule coverage before wider rollout."

## 3. Card-by-card talking points

### THE PROBLEM
- Don't lead with technology — lead with the failure mode: *"a migration a
  person already finished and shipped still had a production secret
  committed to it."* That's the memorable line.
- Named risks, in plain terms: inconsistency across apps, no audit trail,
  defects that surface in production instead of review.

### THE SOLUTION
- Anchor on **one word: bounded.** Seven stages, always in the same order;
  the LLM step only ever sees files the deterministic rules already
  flagged — it cannot wander off and "improve" something nobody asked about.
- "Config-driven, zero code changes" is aimed at whoever's worried about
  vendor lock-in or being stuck with a single hardcoded target app — hit it
  if the audience includes anyone thinking about scale.
- Mention the Migration Workbook briefly as "removes the spreadsheet nobody
  wants to own" — leadership tends to respond to that one concretely.

### PROVEN RESULTS
- The 12 BLOCK / 14 HIGH number is the single most important stat in the
  room. Say it slowly. Follow immediately with: *"this was not a hypothetical
  legacy app — this was live, deployed, and had already passed human review."*
- 9/15 files safely improved, 6 reverted — say this proactively, don't wait
  to be asked. It's not a weakness, it's the safety net visibly working:
  *"when the model's edit wasn't good enough, the tool caught it and kept
  the safe version instead — nothing bad ever reaches the output."*
- 86.3% vs. 90% target: frame as **transparency, not failure.** "We know
  exactly which files it differs on, and why — that's the point of scoring
  it at all."
- "Never guesses" — this is the trust argument. Say explicitly: a tool that
  invents a resource group name is worse than one that stops and asks.

### GOVERNANCE & SAFETY
- This card exists to pre-empt the #1 leadership objection: *"what can this
  break?"* Answer, in order: it can't write to a cluster, it can't push to
  git, your source is read-only. Nothing ships without a human merging a PR.
- The LLM question has gotten harder, not easier, to answer honestly — it
  IS mandatory now, and it CAN write files. Don't undersell that. Lead with
  the safety net instead: *"every single edit it makes is re-validated
  afterwards, and if it fails, it's reverted automatically — the model
  never gets the last word, the validator does."*
- The freeze/idempotency point belongs here too if there's time: *"once
  we've reviewed and approved an output, we can lock it — the same input
  will never produce a different result after that point, even though the
  model itself isn't inherently deterministic."* This is the single best
  answer to "how do we trust an LLM in a compliance-sensitive pipeline."

### EVERY RUN DELIVERS
- Reframe as **audit evidence**, not just files: every run leaves a
  timestamped, reproducible trail — useful for both the migration itself and
  proving governance/compliance later.
- The verdict (AUTO_APPROVE / NEEDS_REVIEW / BLOCK) is the one line that
  makes this CI-gateable — and it's computed from rule severities only,
  never from anything the LLM wrote. Say this explicitly if asked "does the
  AI decide whether this ships" — the answer is no.

### ROADMAP & THE ASK
- Keep "Now" honest: mandatory LLM + freeze proven end-to-end, one proven
  application, Phase 1 target not yet hit (90% vs. 86.3%) — credibility
  comes from not overclaiming.
- The ask must be concrete and bounded: name a number of applications, a
  timeframe, and what you need from them (access to a couple more repos,
  time from one engineer to validate rule coverage). Vague asks don't get
  sponsored.

## 4. Anticipated questions

| Question | Answer |
|---|---|
| "Does this replace our migration engineers?" | No — it replaces the manual discovery/audit grind so engineers spend time on judgment calls, not repetitive checks. Every BLOCK/NEEDS_REVIEW still needs a human. |
| "The LLM writes files now — what if it's wrong?" | Every edit is re-validated after generation (a sanity check, then the full `helm lint`/`kubeconform`/`conftest`/`trivy` suite). A failed edit is automatically reverted to the deterministic rule-engine output and logged as finding `L3` — it's never silently kept. |
| "Can it touch our production cluster?" | No. No apply path exists in this release; source is mounted read-only; nothing is pushed to git. |
| "What does it cost / what does it need?" | The default provider is Ollama — local, no API key, no per-call cost — but it does need to be installed and running (see Prerequisites in the README). No cluster access or cloud account is required either way. |
| "Why isn't the golden score at 100%?" | Because it's a superset, not a copy — it's expected to flag *more* than the human migration (that's remediation working). The score is judged `≥`, not `==`, against the human baseline. |
| "Is the LLM's output deterministic? Can we trust the same result twice?" | Not inherently — which is why we built the freeze mechanism. Confirm a result once, set `FREEZE_OUTPUT=true`, and every run after that replays the same cached response per file — verified with matching file hashes across separate runs. |
| "Does the AI decide whether a migration ships?" | No. JUDGE — the stage that decides AUTO_APPROVE/NEEDS_REVIEW/BLOCK — reads only the severity of findings from the deterministic rules and the validators. It never reads anything the LLM wrote. |
| "How long until this scales to all our apps?" | Onboarding an app is a YAML addition to `config/env-matrix.yaml`, not new code — the roadmap ask is validating rule/mapping coverage on a few more real apps first. |
| "Can we swap in our enterprise-approved LLM?" | Yes — one line in `config/models.yaml` (`provider: azure_openai`/`openai`/`anthropic`/`ollama`). The engine only ever calls a common interface; vendor SDKs are isolated to one folder. |

## 5. If you need more than one slide (backup deck outline)

The one-pager is deliberately the whole story for a leadership readout. If a
follow-up technical session is requested, don't add slides to *this* deck —
build a short backup deck from these sections instead, pulling detail
straight from the [README](../README.md) and
[`AGENTIC_FRAMEWORK.md`](../AGENTIC_FRAMEWORK.md):

1. Architecture — the seven-stage agent loop (Discover / Transform /
   Remediate / **Refine (LLM)** / Render / Validate / Judge) and why the
   LLM is mandatory but still never makes the final call.
2. Rule catalogue — walk `config/rules.yaml` (T1–T8, M1–M9, plus L1–L3 for
   the LLM refine stage) with one real example finding each.
3. Live demo — `./run.sh demo` end to end, then `./run.sh report`. Consider
   running it once already frozen (`FREEZE_OUTPUT=true`) beforehand so the
   live demo takes seconds, not minutes — explain that trade-off honestly.
4. The Migration Workbook — show `migration-intake.example.txt` →
   `migration_workbook.md`, and the storage/network mapping tables in
   `config/mappings.yaml`.
5. Safety + idempotency model — read-only mounts, no apply path,
   `NEEDS_INPUT` philosophy, validate-after-generate, and the freeze/cache
   mechanism (`AGENTIC_FRAMEWORK.md` §4–5).
6. Roadmap detail — hosted-provider evaluation, Connected mode (live
   cluster dry-run + RBAC checks), what each requires.

## 6. Before you present — checklist

- [ ] Re-run `./run.sh demo && ./run.sh golden` and refresh the numbers in
      `build_onepager.py` if it's been a while (rules/fixtures/model may
      have changed). Regenerate with `python presentation/build_onepager.py`.
- [ ] If presenting live, consider running once beforehand with
      `FREEZE_OUTPUT=true` so the on-stage run replays in seconds instead of
      taking minutes to generate fresh — and be ready to explain why, if asked.
- [ ] Have `./run.sh report` output (or `aks/validation.md`) ready to show if
      asked to go one level deeper without a full backup deck.
- [ ] Know the one number you'll repeat if you remember nothing else:
      **12 blocking defects found in a migration a human already shipped.**
- [ ] Know the ask, in one sentence, before you open the room.
